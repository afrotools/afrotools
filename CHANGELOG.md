## [Unreleased]

### Added

- afro.tools Studio, plugin 1.9.0: Studio offers itself when the user describes an app or a service to create for an African market (even with notes or mockups in the folder), and asks before starting; adding a provider to an existing app stays with the category skills, and `check`, `review`, `diagnose` stay manual. The start phase always plays the idea back for confirmation before proposing providers, always asks about a registered business or merchant account (to check with each provider before signing up), and handles needs the registry does not cover: wait for the registry or use a provider outside it (said clearly to have no afro.tools spec), a `request_spec` the user makes anonymous or followed through a GitHub issue, with or without a provider (capability and country), and `pending:` needs checked again on every resume. The plan includes a login from the host or a recognised service and, with payments, a page of pending and failed payments; going live turns on the host's backups and a way back to the previous version. The category skills point an app idea to Studio, and implement a provider the user chose outside the registry from its own documentation, with a warning and no second request. They also log a need with no provider named (capability and country, e.g. USSD in Senegal), and no longer tell the user a request was logged when it was not. Studio also says where the user is at every start, keeps the plan's screens as a checklist ticked during the build, builds the screens that need no provider first so keys never block it, makes a save point before a risky fix and stops after three attempts at the same error, offers its three companions in one message at the start (one restart instead of three), gives orders of magnitude of the usage per phase, decides where the data lives with the stack and the hosting, offers to open the app on the phone, takes a developer's whole brief at once at the quiet level, reads the host's documentation for the production keys and the domain when going live, and finds its key scan through `${CLAUDE_PLUGIN_ROOT}`. A default stack recipe (`references/stack.md`): Next.js on Vercel with the functions in Frankfurt, Tailwind CSS v4 with the design direction written as theme tokens and shadcn/ui components added one at a time (dialogs, selects, forms), fonts self-hosted through `next/font`, a Neon database created from Vercel (a `dev` branch for the computer, a branch per preview with GitHub), drizzle on the `pg` driver with versioned, additive migrations run on deploy, Better Auth (email and password for the owner, sign-up closed after the first account; phone codes sent through the registry's SMS provider, counted per phone number and per hour in the database), Vercel Blob when the plan has files; the agent never reads or edits `.env` and generates secrets with a shell command whose output is not shown; the plan phase says that a host's free plan may forbid a commercial app and asks early whether the user has a card that pays the host; the ship phase follows the recipe's order (the Vercel CLI for a non-developer, GitHub for a developer; the database joined to the project, the plan, production variables entered as secrets, the webhook address, the domain, where Neon's instant restore and Vercel's instant rollback are and what each gives back); a developer path on their own server (Docker Compose, Postgres, a reverse proxy, off-server backups). Every screen ships with its states, built with it: empty, loading, error, offline, form errors on the field, session expired without losing the work, and three payment states worded by the rules (pending until the server has the confirmation, not confirmed, confirmed with what happens next); the browser check looks at the empty and error states too. `check` also flags other people's data readable without login and unlimited login attempts (with Better Auth, a rate limiter kept in memory, or a sign-up route left open), and pre-approves its own script, and the category skills offer `/afrotools:check` once a provider is wired.

- afro.tools Studio, plugin 1.8.0: `/afrotools:studio` takes an app from an idea to production for African markets, in five phases (start, plan, design, build, ship), at an explain or quiet level, with six rules (payment confirmed server-side with the amount compared, nothing paid twice, no key in the code or the browser, messages a stranger can trigger limited per number and per hour; code review and security audit strongly advised, never forced). The build saves a local git save point after each working feature. The start phase suggests asking each provider for production access early, without stating documents or delays the registry does not give. The design phase shows two directions of the main screen and has the chosen one critiqued before any code; paying and receiving a message stay manual tests the user does, with steps Studio gives. Its phases were played on a sewing-workshop app built from scratch, by an agent playing a non-developer, up to a real sandbox payment link and the pre-production check; the code review, the security audit and going live were not exercised.

Orange Money Mali, PayGate and Africa's Talking are unchanged (docs private or blocked).

### Fixed

- **Ids in a URL.** A new or edited canonical example passes an id it puts in a URL through `encodeURIComponent`, as the decoded value, with no format check or validation helper: the format is the provider's to check, and the gotcha says where the id comes from and what is left (an empty value, `.` or `..` still changes the path; an id encoded twice breaks the request). A base64 id (`+`, `/`, `=`, like LengoPay's `pay_id`) is left as is unless a test shows the provider decodes it. The `CLAUDE.md` rule replaces #47's rule against `encodeURIComponent` on path parameters. Applied to Bictorys `verify_transaction` and `capture_charge`, Djomy `get_payment_link`, KadevPay `verify_payment`, Paycard `verify_payment` and `webhook_payment_completed` (whose `assertPathSegment` functions and uuid checks, from #158, #187 and #192, are removed) and Notch Pay `get_beneficiary` and `delete_beneficiary` (#201); Djomy `verify_payment` and `confirm_otp`, with gotchas on where the id comes from — after a payment link, Djomy adds `transactionId` to the `returnUrl` (#200). Paycard and Djomy `verify_payment` stay `verified` with maintainer-approved `spec_hash` values. The older examples follow in 43 call sites: Wave, Notch Pay, Flutterwave, NimbaSMS, Intron, Infobip (2FA) and Smile ID; the Notch Pay `get_customer` and `update_customer` gotchas no longer say to pass the id without encoding, but to store it as returned and never pass an already-encoded value. LengoPay `get_balance` keeps `websiteId` raw (its format is undocumented, and LengoPay's ids, like `pay_id`, are base64). Smile ID `get_smile_link` and `get_verification_status` stay `verified` with maintainer-approved `spec_hash` values (#202).

### Added

- ATSS 1.1 `parameters` (path, query and header parameters; `input_schema` stays the body) and `success_condition` (the response field that says a 2xx call succeeded). `validate` checks every path parameter fills an `endpoint.url` placeholder and every placeholder has one, that a parameter is not also a body field (and a GET/DELETE with parameters has no body), and that `success_condition` names a field of `response_schema` with values of its type. It warns on a payment POST that moves money without a word on idempotency (14 specs today), and on a 1.1 spec whose URL has placeholders but no `parameters` yet (the migration list). No spec uses the new blocks yet; plugin 1.7.1 points the spec skill at them.

### Fixed

- `scripts/test_live.py` checks the whole response, not its top-level keys: it validates the body against `response_schema` with `jsonschema` (types, nested fields, the `oneOf` branch the response matches — replacing the intersection of the variants' `required`, often empty) and fails a 2xx whose `success_condition` is false (e.g. HTTP 200 with `{"code": 1}`). A `$name.field` from a failed earlier step now fails the step in `query_params` and `body` too, not only in path params and headers, and so does an `endpoint.url` placeholder no `path_params` fills. A 204 or non-JSON body no longer crashes the run. `--report FILE` writes a JSON report (per step: HTTP status, result, errors, tested `spec_hash`; date, registry commit, CI run URL); the `Live test` workflow keeps it as an artifact. New requirement: `pip install jsonschema`. The fixture key `discriminated_union` is gone (`jsonschema` matches the branch itself).
- **SasPay**: 4 specs marked fields with OpenAPI 3.0's `"nullable": true`, which JSON Schema 2020-12 ignores — a `null` `checkout_session` or `payment_link` in `verify_payment` broke `type: "string"`, and the `fee_charge_mode` enum of `create_payment`, `create_checkout_session` and `send_payout` excluded `null`. Now `"type": ["string", "null"]` (with `null` in the enum). `validate` rejects `nullable` in a spec's schemas. The three `verified` specs keep their status, with a maintainer-approved `spec_hash`.
- **LengoPay** `webhook_payment_completed`: the example and the first gotcha verified payments with `GET /api/v1/payments/{payId}`, replaced in v1.2.0; they now call `POST /api/v1/transaction/status` like `verify_payment` and the example app (#130). Stays `verified`, with a maintainer-approved `spec_hash`.
- **NimbaSMS**: the `list_sendernames` example filtered on status `active`, which the API never returns (`pending`, `refused`, `accepted`); `verify_code` no longer claims 4 to 6 digits, and records the docs' own 4-to-8 vs `maximum: 999999` contradiction as an open question (#129).
- `scripts/validate.js` rejects a provider slug reused in another category, in every mode (`--changed` included): the registry, the MCP and the website index providers by slug alone, so the second provider silently shadowed the first. CI now runs `scripts/validate.test.js`.
- `scripts/test_live.py` no longer reports success when calls fail: a step fails on an unexpected HTTP status (default: non-2xx, overridable per step with `expected_status`), and a skipped step (missing schema, or a path param or header from an earlier step that returned nothing) fails the run. Before, a run where every call got a 401 printed "live responses match the spec ✓" and exited 0 whenever the response schema had no `required` field. Offline tests in `scripts/test_live_test.py`, run in CI.
- Plugin skills (1.5.1): discovery starts with `list_providers()` (exact capability names per provider) and keeps a filter on `search_specs` — a whole-category search returned more than the MCP client shows inline. The payment skill no longer hardcodes `create_payment` / `verify_payment` / `webhook_payment_completed` (7 of 12 payment providers name them differently), and a `get_spec` "not found" no longer ends in "spec not available". `/afrotools:list` called `list_specs`, a tool that never existed; it now uses `list_providers` / `search_specs`. CI checks that skills only call tools the MCP exposes.
- **Flutterwave** (v4) rewritten from the OpenAPI embedded in its API reference (snapshot 2026-10-25), after an
  adversarial review found 17 blocking errors in the previous specs (e.g. transfer webhook status `succeeded` instead of
  `SUCCESSFUL`, invented fields on the orchestrator transfer, `X-Trace-Id` claimed required, wrong error codes). Every
  spec now has an `evidence` block and every quoted doc sentence is checked against the snapshot.
  - **BREAKING:** 25 rarely used capabilities removed (orders/pre-auth, list/get/delete helpers, wallet statement,
    fees, settlement by id, test-only `create_chargeback`, …); 32 kept and `resend_webhook` added (33).
  - `currency` uses `SLL` for Sierra Leone (the only code Flutterwave's API accepts) and adds USD (card charges,
    USD bank payouts); provider countries add CG, EG, ET, MW, TD (from its bank and mobile-network endpoints).
- `scripts/validate.js` accepts the pre-redenomination code `SLL` as Sierra Leone's currency (`LEGACY_CURRENCY_CODES`).
- `scripts/test_live.py` compares a response whose `data` is a union (`oneOf`) against all of its variants, and its
  default `X-Trace-Id` is alphanumeric (`afrotoolslive<ms>`; Flutterwave accepts only alphanumeric trace ids).

- `scripts/test_live.py` sends an explicit `User-Agent` (Cloudflare-fronted sandboxes such as
  Smile ID's ban urllib's default with error 1010) and skips a step whose headers depend on an
  earlier step that returned nothing, instead of crashing.
- `scripts/test_live.py` fixtures: per-step `wait_seconds` (e.g. let an async job become visible
  before reading its status). Live-test workflow uses `actions/setup-python@v6` (Node 24).
- **Wave** (issue #76): the webhook example now records the event before answering 200 (and answers 500 if that fails,
  so Wave retries), handles both webhook security modes (Signing Secret and Shared Secret), and no longer claims Wave
